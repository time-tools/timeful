## Description

## Outcome

Stop downloading and executing the `temporal-polyfill` JavaScript on engines that already provide native `Temporal`, while preserving the existing Temporal runtime behavior and ADR-004's single runtime model for engines without it.

## Context

- The frontend imports the temporal-polyfill ponyfill entrypoint in roughly 100 files; 1.x delegates to native `Temporal` at runtime where available, but the polyfill code is always bundled and downloaded.
- The Temporal implementation lands in a shared chunk of roughly 60 KB raw / 21 KB gzip that is part of the eager graph.
- Native `Temporal` ships in Firefox 139+, Chrome 144+, and Node 26+; Safari/WebKit relies on the JS polyfill until it ships native `Temporal`.
- ADR-004 defines the runtime model, ADR-006 covers value-semantics helpers, and `frontend/AGENTS.md` requires runtime verification because typecheck and build alone are not sufficient for Temporal behavior.
- TASK-0116.02 covers dropping the dependency once WebKit ships native `Temporal`; TASK-0116.03 covers temporal-polyfill/fns tree-shaking. This task covers native-first conditional loading only.

## Constraints

- No behavior change under ADR-004; contexts that lack native `Temporal` must keep working exactly as today.
- Many Temporal regressions are runtime issues; exercise the app flows that depend on Temporal, not only tests.
- Re-measure the latest `temporal-polyfill` entrypoint options at execution time before choosing an approach.
