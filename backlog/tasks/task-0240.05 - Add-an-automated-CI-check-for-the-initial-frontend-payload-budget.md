## Description

## Outcome

CI measures the frontend's initial eager payload from the production build and fails when it exceeds the committed budget, so payload regressions are caught before merge.

## Context

- The metric is the JavaScript and CSS fetched before first render on the Landing and guest Event entry routes, derived from the production build's entry HTML and modulepreload graph; this is the same metric QR-015 (TASK-0241) records.
- `.github/workflows/frontend-ci.yml` already installs and builds the frontend, and `docs/ci.md` documents each workflow.
- The recorded pre-improvement eager payload is roughly 1.1 MB raw / 319 KB gzip, including CSS.
- This task does not need the bundle-size reductions to be complete before starting; the initial check can land with thresholds set from the baseline measured at execution time.

## Revision trigger

When TASK-0240 lands, its subtasks reduce the eager payload, and thresholds set against the pre-improvement baseline would then allow the reduced payload to grow back to the old size.
Re-measure the post-improvement eager payload, revise the committed thresholds to that baseline, reconcile the metric with QR-015 (TASK-0241), and record the revision in this task before finalizing it.
If this task is executed after TASK-0240 already landed, set the initial thresholds from the post-improvement baseline and record that no revision was needed.

## Constraints

- Keep the measurement reproducible locally and in CI, with thresholds stored in one committed location and a documented revision procedure.
- Fail only on budget regressions; unrelated build warnings must not fail the check.
- Do not encode thresholds in workflow YAML alone; developers must be able to run the same measurement locally.
- Do not change runtime code or application behavior.
