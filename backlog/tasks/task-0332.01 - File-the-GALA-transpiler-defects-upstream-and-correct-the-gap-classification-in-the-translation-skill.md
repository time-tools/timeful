## Re-verification on 0.84.1

All three defects re-derived from scratch rather than trusted from the task notes, because a release may have lifted one and the skill's own rule requires it. Compiler `gala` 0.84.1 (latest release, 2026-09-28; the local checkout of the compiler source is 68 commits behind `upstream/master`, but the released compiler on `PATH` is current), Go go1.26.7.

**`fallthrough` in a `match` arm.** Reproduces exactly. A bare `fallthrough` statement is rejected with `GALA-E0036` and a hint; the same word in a `match` arm reaches codegen and produces `GALA-E0017`, with the unparseable output written to `/tmp/gala-unparseable-arm-*.go` and named in the error. Exit status 1. The generated Go contains `return fallthrough` inside the lowered arm.

Getting the repro to reproduce took correcting the `match` spelling twice: `match n { ... }` is not the syntax, the subject precedes the keyword (`n match { case ... }`), and an arm body is an expression rather than a `return`. The wrong spellings fail with ordinary parse errors, which is worth remembering, because a parse error looks like a different construct being unsupported.

**`match` over a struct with `var` fields.** Reproduces, and the emitted Go makes the bug unusually legible. The `var` spelling emits `Unapply(v any) (int, int, bool)` with plain `int` fields, yet the match lowering emits `x := obj.X.Get()`. The non-`var` spelling emits `Unapply(v any) (std.Immutable[int], std.Immutable[int], bool)` with `std.Immutable[int]` fields, and the identical `.Get()` is correct there. So the transpiler generates the signature that states which case applies and then ignores it. `go build` fails on the first, `go run` prints `origin 0 0` on the second.

The same two corrections applied here: a struct pattern over a non-sealed struct needs a `case _ =>` arm or `GALA-E0003` fires first and masks the bug, and the constructor is positional (`Point(0, 0)`), not `Point(X: 0, Y: 0)`.

**`.Size()` on a field of a Go-declared struct.** Reproduces in a mixed package, which is the case PR #529 predicted. The trigger is narrower than the skill recorded and also broader: it is not specific to slices, because a plain `string` field of a Go-declared struct fails identically, while a direct field read still works. So it is the interop call that needs the field type and gets none, not the field access.

One correction to the earlier note: `.ByteSize()` on a slice is not the same defect. The specification scopes `.ByteSize()` to strings, and on a GALA-declared struct a `.Size()` on a `[]string` field lowers correctly to `len(b.Items)`. The skill's original entry named both methods as failing in the pure case, which was wrong; the entry now names `.Size()` and says the trigger is an unresolved receiver.

## The blocked-construct plan was wrong, and the tracker is why

The handoff planned to add the blocked constructs to #528 as construct entries. Reading the tracker first showed that would re-report answered items, which the skill's own report template forbids. The blocked list has 22 rows, not 20.

- Eight are already triaged and answered in #528: struct tags, multi-value return signatures, anonymous struct types, `struct{}` as a type expression, channel types, embedded fields, fixed-size arrays, `select` and `recover` (the maintainer gave a GALA equivalent for each), plus a method on a defined type as GAP-4, now GALA-E0048.
- Four more are named in PR #529 as having documented replacements: `switch`, `interface{}`, type assertions, fixed-size arrays.
- The rest are refused with a coded diagnostic whose hint states the fix (E0034, E0052, E0003, E0035), or are a documented semantic.
- `const` is the only row that is a gap in the sense the file means by the word, and even it has a substitute for everything except a value that must stay a Go compile-time constant.
- Assignment to a `:=` binding is not a gap at all: `docs/GALA.MD` states that `:=` bindings are immutable, and the rejection is the specification working as written.
- A Go function literal inside a composite literal was never a gap: the Go spelling is a parse error, and a GALA lambda in that position transpiles and builds.

No comment was posted to #528. The user chose to correct the skill's list instead, which is the right order: the list was the thing that was wrong, and fixing the source prevents the next reader from filing the same duplicates.
