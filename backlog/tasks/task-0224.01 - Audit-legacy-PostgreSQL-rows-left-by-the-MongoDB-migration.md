## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Phase 1 of TASK-0224. The compatibility code named in the parent description exists to tolerate legacy row shapes from the MongoDB era, but no database has ever been audited to establish which shapes are actually present. Databases created from the current baseline have no legacy rows; the targets are deployed databases (and retained backups) that may predate it.

Outcome: a repeatable, read-only audit that classifies every compatibility-shaped legacy row in each deployed PostgreSQL database and records the counts as evidence for the later phases. The audit must not modify data. Where a database predates the baseline, the recreate-from-baseline policy in docs/postgres-operations.md applies instead of in-place cleanup; record that state rather than attempting repairs here.

The seven classes to classify:
1. postgres_events.name that is empty or longer than 100 characters.
2. calendar_preferences.calendar_options that is not a valid JSON object.
3. calendar_accounts.calendar_key values that are not canonical (for example mixed-case email prefixes).
4. postgres_event_responses.respondent_kind that is NULL or empty.
5. postgres_events and postgres_event_responses rows with populated guest_id, guest_edit_policy, guest_ownership_mode, or guest_edit_token.
6. Stored JSONB payloads carrying account or event identifiers that are not canonical UUIDs.
7. Rows whose parent is missing (orphans) across event, response, attendee, signup, signup-membership, folder, calendar, and daily-log relations.
<!-- SECTION:DESCRIPTION:END -->
