## Description

## Outcome

Prove the procedure works by using it, on a real server file, and record what the procedure failed to say.

Authoring a playbook and instrumenting the roster are both untested claims about a workflow.
Only an actual rewrite distinguishes a procedure that is executable from one that merely reads well, and a pilot is where the gaps no probe covers surface: which trap was not stated plainly enough, which step was ambiguous, which verdict turned out to need a judgement the roster does not record.
Those findings are the input to whatever the procedure needs next, so this task is scoped to produce a verdict as well as a twin.

`routes` is the natural first target: it already carries a GALA twin and a handwritten sibling, so the mixed-package layout the procedure must describe is a layout that already exists rather than one this task introduces.
A preflight-clean candidate elsewhere in the server module is equally acceptable, and the preflight output is what decides.

This task depends on TASK-0330.03 for the procedure it follows, on TASK-0330.02 for the catalog, and on TASK-0330.01 for the preflight that selects the candidate.

## Requirements

- A candidate is chosen from the files preflight reports as rewritable, and the choice and its preflight output are recorded in the task notes.
- The file is rewritten by following the playbook steps in order, without a bespoke path around them.
- The committed twin is generated from its `.gala` source by the documented command and is not hand-edited.
- Whether the rewrite needed a split with a handwritten sibling, and if so which members moved, is recorded.
- The server builds, the affected package's tests pass, and regenerating the twin twice produces byte-identical output.
- Every document and table that must gain a row or a count for a new twin gains it, and the roster's inventory counts are re-derived rather than hand-edited.
- The roster, the audit script, and the inventory drift check pass after the change.
- Gaps the pilot exposed in the procedure are recorded in the task notes as findings for a follow-up, and the procedure is corrected in place where a gap is small and unambiguous.

## Constraints

- This task consumes the procedure; it does not extend the roster's verdicts.
  A new verdict, probe, gap class, or `GAP-n` entry is out of scope and belongs in its own task.
- GALA 0.81.0 and the Go 1.26 series stay the pinned toolchains, and the vendored runtime under `server/third_party/gala/` is not modified.
- The generated twin's Go-facing behaviour, exported signatures, and wire shapes are preserved exactly.
  A rewrite that changes what a Go caller or a JSON payload sees does not satisfy this task, and a candidate whose preflight verdict is `keep handwritten` is not a candidate.
- If preflight reports the chosen candidate as needing a handwritten sibling, that is an expected outcome rather than a failure.
- The procedure is followed as written.
  A shortcut taken because a step was unclear is itself a finding to record, and is not a reason to silently rewrite the procedure mid-task.
- The isolated Compose test stack is required rather than optional, because the affected package's tests are PostgreSQL-backed; the canonical command sequence lives in `server/README.md`.
- The Bug Fix Protocol in `AGENTS.md` does not apply, because this is a rewrite rather than a defect fix; the regression-check requirement is replaced here by the twin's own build, test, and double-regeneration evidence.

## Evidence required

- The preflight output for the chosen candidate, the transpile, build, test, and double-regeneration results, the audit and inventory check output, and the record of any procedure gaps, all in the task notes.
