## Outcome

Give an agent an ordered, self-contained procedure for turning one Go server file into a GALA twin, ending with an explicit definition of done for that file and an explicit condition under which it must stop and leave the file handwritten.

The roster answers "what does GALA do with this Go construct", and `server/GALA.md` records what worked and what did not during the spikes, but neither is a procedure.
A rewrite attempt today has to infer its own order of operations, its own verification loop, and its own stopping point, and that inferred procedure is unverified.
Without a stated stop rule an agent attempts files the roster classifies as untranslatable and either fails repeatedly or silently reshapes a wire-facing Go API.

This task depends on TASK-0330.01 for the preflight command it must instruct the reader to run, and on TASK-0330.02 for the mechanical rewrite catalog its rewrite step must point at.
Both must be merged first, because a procedure that cites a tool or a section that does not yet exist is worse than no procedure.

## Requirements

- The page states its preconditions: the pinned GALA and Go toolchains, the vendored runtime, and the fact that both the `.gala` source and the generated Go twin are committed because the Go build never invokes GALA.
- The page gives the ordered procedure from candidate selection to registration, with each step naming the exact command or file it acts on.
- Pre-triage of a candidate is a named step, and the page says what to do with each possible outcome.
- The output-style choice is a named step, covering the runtime-free and runtime-enabled styles and the two shape rules that constrain them: an exported package-level `val` changes the Go type a Go caller sees, and a GALA struct declaration is not a drop-in twin.
- The twin layout rules are stated: the `.gala` source beside the generated `.go`, the package comment in a handwritten `doc.go`, a handwritten sibling for members GALA cannot express, no hand-editing of a generated file, and each `.gala` file importing what it uses.
- The per-twin verification loop is its own step, distinguishing the transpile-from-the-package-directory requirement that keeps `//line` directives relative, the server build and tests, byte-identical regeneration, and the corpus and inventory checks.
- Registration of a new twin is a named step, naming every document and table that must gain a row or a count.
- Abort rules are explicit, and a trap list covers the rewrites that transpile cleanly but fail at build or at the Go call boundary, including the `.Size()`-on-a-field-whose-type-lives-in-a-handwritten-sibling failure specific to a mixed `.gala` and handwritten `.go` package.
- The page ends with a definition of done for a single file.
- The page is reachable by inbound link from `server/GALA.md` and `server/README.md`, which is how a flat page in `docs/` is discovered in this repository.

## Constraints

- The roster, `server/GALA.md`, and the probe corpus stay the sources of truth for verdicts.
  This page must not become a fourth copy of them, and it must not restate a construct verdict, a probe name, or an occurrence count.
- Nothing is changed in the roster, the corpus, or any committed twin by this task.
- Claimed commands, file paths, and tool behaviour are verified against the repository as they are written, not recalled from the spike sessions.
  In particular the transpile command, the canonical backend test sequence, and the corpus and audit entry points must be checked against the files that own them.
- Root Markdown follows the sentence-per-line and table-row rules in `docs/AGENTS.md`, and terminology follows `docs/terminology/README.md`.
- Every `GAP-n` identifier and probe name the page cites resolves, and the roster's audit script is the check for that.
- The page is documentation only: no runtime code, no build or deployment configuration, no generated artifact.

## Evidence required

- The formatting and lint checks, and the audit script, recorded in the task notes.
- A read-through confirming every cited path, command, and identifier exists, recorded in the task notes.
