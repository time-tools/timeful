## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Outcome

Give an agent an ordered, self-contained procedure for turning one Go server file into a GALA twin, ending with an explicit definition of done for that file and an explicit condition under which it must stop and leave the file handwritten.

The roster answers "what does GALA do with this Go construct", and `server/GALA.md` records what worked and what did not during the spikes, but neither is a procedure.
A rewrite attempt today has to infer its own order of operations, its own verification loop, and its own stopping point, and that inferred procedure is unverified.
Without a stated stop rule an agent attempts files the roster classifies as untranslatable and either fails repeatedly or silently reshapes a wire-facing Go API.

This task depends on TASK-0330.01 for the preflight command it must instruct the reader to run, and on TASK-0330.02 for the mechanical rewrite catalog its rewrite step must point at.
Both must be merged first, because a procedure that cites a tool or a section that does not yet exist is worse than no procedure.

## Requirements

- The page states its preconditions: the pinned GALA and Go toolchains, the vendored runtime, and the fact that both the `.gala` source and the generated Go twin are committed because the Go build never invokes GALA.
- The page gives the ordered procedure from candidate selection to registration, with each step naming the exact command or file it acts on.
- Pre-triage of a candidate is a named step, and the page says what to do with each possible outcome.
- The output-style choice is a named step, covering the runtime-free and runtime-enabled styles and the two shape rules that constrain them: an exported package-level `val` changes the Go type a Go caller sees, and a GALA struct declaration is not a drop-in twin.
- The twin layout rules are stated: the `.gala` source beside the generated `.go`, the package comment in a handwritten `doc.go`, a handwritten sibling for members GALA cannot express, no hand-editing of a generated file, and each `.gala` file importing what it uses.
- The per-twin verification loop is its own step, distinguishing the transpile-from-the-package-directory requirement that keeps `//line` directives relative, the server build and tests, byte-identical regeneration, and the corpus and inventory checks.
- Registration of a new twin is a named step, naming every document and table that must gain a row or a count.
- Abort rules are explicit, and a trap list covers the rewrites that transpile cleanly but fail at build or at the Go call boundary, including the `.Size()`-on-a-field-whose-type-lives-in-a-handwritten-sibling failure specific to a mixed `.gala` and handwritten `.go` package.
- The page ends with a definition of done for a single file.
- The page is reachable by inbound link from `server/GALA.md` and `server/README.md`, which is how a flat page in `docs/` is discovered in this repository.

## Constraints

- The roster, `server/GALA.md`, and the probe corpus stay the sources of truth for verdicts.
  This page must not become a fourth copy of them, and it must not restate a construct verdict, a probe name, or an occurrence count.
- Nothing is changed in the roster, the corpus, or any committed twin by this task.
- Claimed commands, file paths, and tool behaviour are verified against the repository as they are written, not recalled from the spike sessions.
  In particular the transpile command, the canonical backend test sequence, and the corpus and audit entry points must be checked against the files that own them.
- Root Markdown follows the sentence-per-line and table-row rules in `docs/AGENTS.md`, and terminology follows `docs/terminology/README.md`.
- Every `GAP-n` identifier and probe name the page cites resolves, and the roster's audit script is the check for that.
- The page is documentation only: no runtime code, no build or deployment configuration, no generated artifact.

## Evidence required

- The formatting and lint checks, and the audit script, recorded in the task notes.
- A read-through confirming every cited path, command, and identifier exists, recorded in the task notes.

## Plan

Both dependencies are merged and green at HEAD: `go run ./inventory -check` reports `doc matches (166 files)`, `audit.sh` reports six `ok` lines and `audit passed`, and `go test -count=1 ./inventory/` passes.

### Page

New flat page `docs/gala-rewrite-playbook.md`, ordered steps from candidate selection to registration, then abort rules, traps, and a per-file definition of done.

1. Preconditions: the pinned `gala` version, the Go toolchain series `run.sh` pins, the vendored runtime and its `replace` in `server/go.mod`, and the committed-both-artifacts rule.
2. Step 1 select a candidate: pick a leaf file in a package that already has a GALA source, read its package's entry in the roster's ladder rung, read `server/GALA.md` for the package's committed style.
3. Step 2 pre-triage: `go run ./inventory -preflight ../../<pkg>/<file>.go` from the corpus directory, the decision ladder it prints, and the action for each rung, including the advisory-exit-0 fact and the exit statuses 2, 3, 4.
4. Step 3 choose the output style: the two styles and the two shape rules, pointing at the roster's decision ladder and at `server/GALA.md` for the full list.
5. Step 4 write the `.gala` source: one rule at a time from the roster's `Mechanical rewrites` section, plus the no-rewrite index as the stop signal for a member, and the roster sections for the constructs that are direct forms.
6. Step 5 lay out the twin: `.gala` beside the `.go`, `doc.go`, handwritten sibling, no hand-editing, per-file imports.
7. Step 6 verify the twin: transpile from the package directory, `go build ./...`, the canonical test sequence, `gofmt -l`, byte-identical regeneration, then the corpus, audit, and inventory checks.
8. Step 7 register the twin: the two tables in `server/README.md` and `server/GALA.md`, the roster's inventory summary sentence and table, and the two prose counts.
9. Abort rules, trap list, and the per-file definition of done.

### Constraints honoured

The page cites the roster's sections and links them; it carries no construct verdict, no `GAP-n` identifier, no probe name, and no occurrence count, so it cannot fork the sources of truth.
Every command, path, and exit status is taken from the file that owns it: `run.sh`, `audit.sh`, `inventory/main.go`, `server/README.md`, `server/GALA.md`, and the generated twins themselves.
`server/GALA.md` and `server/README.md` gain one inbound link each; nothing else changes.

## Baseline at HEAD

`go run ./inventory -check` reported `doc matches (166 files)`, `audit.sh` reported six `ok` lines and `audit passed`, and `go test -count=1 ./inventory/` passed, so every check below is a comparison against a known-good baseline rather than an absolute claim.

## What landed

`docs/gala-rewrite-playbook.md` (239 lines) plus one inbound link each in `server/GALA.md` and `server/README.md`. Nothing else in the repository changed.

Structure: preconditions, seven numbered steps from candidate selection to registration, abort rules, a trap table, and a per-file definition of done.

- Preconditions state the four things that silently invalidate a rewrite rather than failing: the pinned `gala` version with its override, the Go toolchain series the corpus pins with its override, the vendored runtime and its local replace, and the both-artifacts-committed rule. The pinned version is left to the two files that own it rather than duplicated as a literal.
- Step 1 names `server/GALA.md` and the roster's decision ladder as the two things to read before forming an opinion, and says explicitly that the file's own appearance does not decide the outcome.
- Step 2 is the pre-triage step: one command, one table mapping each file-level verdict to an action, and a second table mapping exit statuses 2, 3, and 4 to what they mean. It records the two facts that make the tool safe to rely on: the verdict is advisory so the exit status is 0 even for the rung that says stop, and a `not classified in the roster` row does not drive the file-level verdict, so its presence is blocking until the roster covers it.
- Step 3 is the output-style step, with both committable styles and the two shape rules stated in full, because those rules are the reason the style is a decision.
- Step 4 points at the roster's mechanical rewrites as the work list, distinguishes the no-rewrite index from a rule row, points at the contested-verdicts section for the non-mechanical branches, and transpiles to a scratch path first so a parse error costs nothing.
- Step 5 is the layout step: the source-beside-twin rule, the `DO NOT EDIT` header, `doc.go`, the handwritten sibling, and per-file imports.
- Step 6 is the verification step, six ordered sub-steps: transpile from the package directory, `go build ./...`, `gofmt -l`, the canonical backend test sequence, byte-identical regeneration via `git diff --exit-code`, then `run.sh`, `audit.sh`, and `go run ./inventory -check`. It notes that `-check` is expected to fail at that point because a new twin changes the module, and that the failure is the signal for step 7 rather than a defect in the twin.
- Step 7 names every document and count a new twin changes: the transpiled-sources table and handwritten-sibling sentence in `server/README.md`, the current-usage table and the counting sentence above it in `server/GALA.md`, and the inventory summary sentence plus the inventory table in the roster. It also states what does not change, which is the part an agent would otherwise over-edit.
- Abort rules are five conditions, each with its reason, and they say that aborting is a correct outcome.
- The trap table is eight rows, each a rewrite that transpiles cleanly and fails afterwards. The mixed-package `.Size()` failure the task called out is the first row; the bare-name collision with an imported package, the dropped doc comment, and the repo-root transpile are the ones invisible in a build log.

## How the source-of-truth constraint was honoured

The page cites no construct verdict, no `GAP-n` identifier, no probe name, and no occurrence count. It links the roster's four relevant sections by anchor and defers every judgement to them, including the ladder rung labels, which the preflight prints in the roster's own words and which the page tells the reader to read from the tool output rather than from the page.

The ladder rung numbers are used as positions, not as quoted verdicts, and every rung row is paired with an action rather than with the roster's wording for that rung. That was deliberate: quoting the labels would have made the page a place a reader trusts after the roster changes.

Verified mechanically:

```

(no matches)
```

## What landed

`docs/gala-rewrite-playbook.md`, a 239-line agent-facing procedure, plus one inbound link each in `server/GALA.md` and `server/README.md`.

It is preconditions, seven ordered steps from candidate selection to registration, abort rules, a trap table, and a definition of done for one file.
Pre-triage, output-style choice, twin layout, per-twin verification, and registration are each a named step, and the verification step separates transpile, server build and tests, byte-identical regeneration, and the corpus and inventory checks into six ordered sub-steps.

## The decision that shaped it

The page cites no construct verdict, no `GAP-n` identifier, no probe name, and no occurrence count.
It links four roster sections by anchor and defers every judgement to them, including the decision ladder's rung labels, which the preflight prints in the roster's own words and which the page tells the reader to read from the tool output rather than from the page.

That was a deliberate reading of the task's two constraints, which pull in opposite directions on their face: the page must state what to do for each pre-triage outcome, yet must not restate a verdict.
Using rung *positions* paired with an action satisfies both and cannot rot, whereas quoting the labels would have created a fourth place a reader trusts after the roster changes.
Verified mechanically: `grep -nE 'GAP-[0-9]+|\b(pass|blocked|contested|delta)_[a-z_]+'` on the page returns nothing.

Two further pieces of honesty the page carries because they are easy to get wrong:

- The preflight's exit status is `0` for every verdict, including the one that says stop, because the verdict is advisory.
  An agent keying on the exit status would never stop.
- A family row reading `not classified in the roster` does not drive the file-level verdict, so its presence is blocking until the roster covers it, even though the verdict line reads like a decision.

## The trap table

Eight rewrites that transpile cleanly and fail afterwards, each with how it fails and what to do.
The mixed-package `.Size()` failure the task named is the first row.
The rows an agent is least likely to anticipate are the bare-name collision with an imported package, the doc comment silently dropped from generated Go, and the repo-root transpile, because none of them produces a build error at the point of the mistake.
