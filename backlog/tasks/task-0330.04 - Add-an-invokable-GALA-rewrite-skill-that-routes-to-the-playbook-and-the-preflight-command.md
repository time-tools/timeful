## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Outcome

Make the rewrite procedure reachable the way an agent is actually invoked in this repository, without duplicating any of it.

`.agents/skills/` is already the registered skill path and needs no agent configuration change, so a skill here is a pure routing concern.
Its value is that an agent asked to "rewrite this file in GALA" finds the preconditions, the stop conditions, and the exact commands immediately, instead of discovering that the roster exists and then reconstructing an order of operations from an eleven-column table.
Without it the procedure is only reachable if the agent already knows to go looking for it.

This task depends on TASK-0330.03 for the playbook it routes to and on TASK-0330.02 for the catalog the playbook points at.

## Requirements

- The skill loads from the existing registered path and needs no agent configuration change.
- Its frontmatter matches the shape used by the skills already in the repository.
- Its body gives the preconditions, the ordered steps with their stop conditions, the exact commands, and pointers to the playbook, the roster, the spike record, and the probe corpus.
- It states the conditions under which the rewrite must not be attempted, so an agent asked to translate an untranslatable file stops and says so rather than reshaping a Go-facing API.
- It keeps no construct verdict, probe name, or occurrence count of its own; anything it states is traceable to the page it points at.

## Constraints

- The skill is documentation and agent instruction only: no runtime code, no build or deployment configuration, no generated artifact.
- Frontmatter uses only the two keys the existing skills use, and the description follows their trigger-clause shape so the skill is discovered the same way as the others.
- It matches the sentence-per-line rule in `docs/AGENTS.md` by hand, because the repository's Markdown tooling excludes this path from both the formatter and the linter.
- It must not restate the playbook's procedure in a form that can diverge from it.
  Where a step needs a decision, it names the page that holds the decision.
- The path of the playbook page is whatever TASK-0330.03 created; confirm it rather than assuming a name.

## Evidence required

- The skill loading through the agent's skill loader, recorded in the task notes.
- A read-through confirming every cited path and command exists, recorded in the task notes.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
## Plan

One new file, `.agents/skills/gala-rewrite/SKILL.md`, and no other change.

### Frontmatter

`name: gala-rewrite` and `description:` in the trigger-clause shape the three existing skills use, so the skill is discovered by the same query that finds them. The trigger clause names the phrasings a user actually uses for this work, because that is the only thing the description is for.

### The divergence line

The one design decision worth stating up front, because the task's requirements and constraints pull against each other: the body has to carry the ordered steps, the stop conditions, and the exact commands, and it must not restate the playbook in a form that can diverge from it.

The line drawn is between the two kinds of content the playbook holds:

- Commands and paths are exact facts owned by other files. The skill states them verbatim and attributes each to the file that owns it, because a paraphrased command is the divergence risk and a verbatim one is not.
- Decisions are the playbook's. Every step in the skill names the page that holds the judgement, and none of them carries a construct verdict, a gap identifier, a probe name, or an occurrence count.

The stop conditions are the interesting case, because AC requires an agent reading only the skill to know when to stop. The playbook's five abort conditions are procedural rather than verdict-bearing, so restating the conditions forks nothing, and each is paired with a pointer to the playbook's abort-rules section for the reason. This is the same resolution TASK-0330.03 used for the ladder rungs: state the position, delegate the wording.

### Body shape

- What this covers, and the one-sentence form of the whole procedure.
- The four sources of truth by role, so the agent knows which page answers which question before it starts.
- The preconditions, as a check-before-acting list, with the playbook owning each.
- The seven steps, one line each, each naming its command where it has one and linking to the playbook section holding the decision.
- The stop-and-report conditions, stated so the skill is sufficient on its own for the decision to stop.
- A short do-not list for the rewrites that transpile cleanly and fail afterwards, pointing at the playbook's trap table rather than reproducing it.
- A per-file definition of done that points at the playbook's own checklist.

### Verification

- Skill loads through the agent's skill loader, recorded in the notes.
- Every cited path, anchor, and command confirmed to exist; the preflight command executed rather than recalled.
- A grep proving the skill carries no verdict, gap identifier, probe name, or count, matching TASK-0330.03's check.
- The Markdown checks, run to confirm they are no-ops for this path rather than assumed to be.

## How the divergence constraint was honoured

The line drawn is between the two kinds of content the playbook holds, and it is the same resolution TASK-0330.03 used for the ladder rungs.

- Commands and paths are exact facts owned by other files, so they are stated verbatim and attributed to the file that owns them. A paraphrased command is the divergence risk; a verbatim one is not.
- Decisions are the playbook's, so every step names the section that holds the judgement and the skill states none of it.

The stop conditions needed the most care, because the acceptance criteria require an agent reading only the skill to know when to stop, while the constraint forbids restating the procedure. The playbook's five abort conditions are procedural rather than verdict-bearing, so stating them forks no source of truth, and each is paired with a pointer to the playbook's abort-rules section for the reason. The top rung is described positionally as "the one whose roster wording is to keep the file handwritten" rather than by quoting the roster's label, which keeps the ladder's wording owned by the roster.

The backend test sequence is deliberately not reproduced: `server/README.md` declares it canonical and `docs/environments.md` documents its isolation semantics, so a third copy in a skill is a place those commands can drift. The skill names the file to run it from and says why. The trap table is likewise not reproduced; the skill states the class, points at the table, and gives only the two entries that are actions to take or avoid rather than diagnoses to make.

## Read-through of every cited path and command

Paths, all confirmed to exist: `docs/gala-rewrite-playbook.md`, `docs/gala-translation.md`, `server/GALA.md`, `server/README.md`, `docs/environments.md`, `server/go.mod`, `server/third_party/gala/`, `server/scripts/20260923_gala_translation_probes/` with its `run.sh`, `audit.sh`, and `inventory/`, and `BACKLOG_WORKFLOW.md`.

Commands. The preflight was executed rather than recalled, against `server/appenv/appenv_port.go`, and it printed the ladder, one family row per construct, and `file-level verdict: rung 2`.

That run surfaced a fact the playbook does not mention and that the skill now states, because an agent keying on the shell status would otherwise stop for the wrong reason. `go run` does not propagate the tool's exit code: a tool failure prints `exit status <n>` on stderr and the shell sees `1`. Confirmed by building the tool and comparing against the `go run` invocation:

```
$ inv -preflight ../../appenv/appenv_port.gala
preflight: read ../../appenv/appenv_port.gala: open ...: no such file or directory
binary exit=2
$ go run ./inventory -preflight ../../appenv/appenv_port.go >/dev/null
verdict exit=0
```

So the skill states that a verdict yields status `0` including the rung that says stop, and that a non-zero status means the tool could not answer rather than that the file is blocked, delegating the per-status meanings to the playbook. This is additive to the playbook rather than divergent from it, and it is the most useful thing this task contributed beyond routing.

The remaining commands were confirmed against the file that owns each: the transpile flags against `gala transpile --help` as documented in `server/GALA.md`, `go build ./...` and `gofmt -l` against the server module, `git diff --exit-code`, `run.sh`, `audit.sh`, and `go run ./inventory -check`. `gala` is not on `PATH` in this environment, so the transpile was not executed here; TASK-0330.03 executed it three ways and recorded the observations, and the skill attributes the command to those files rather than claiming fresh execution.

The twelve playbook anchors were generated with the repository's own `github-slugger` before writing. The skill ended up referring to the playbook's sections by name rather than by link, because a skill body is read as text by an agent and a name is what it acts on.

## Formatting

The repository's Markdown tooling excludes this path at `scripts/markdown.mjs:19`, so the rule in `docs/AGENTS.md` had to be satisfied by hand, and the objective standard available for checking it is the repository's own sentences-per-line implementation.

Running that implementation against the file found two real problems, both fixed:

- Five bullets carried two sentences each, which the formatter splits into a bullet plus a two-space continuation. Each was rewritten as a single sentence rather than accepting the continuation form, so the file has no continuation lines at all.
- The one table was not column-padded. It was padded by running the repository's formatter over the file, so the padding is the tool's output rather than my arithmetic.

The result is clean under the tool that implements the rule, which is a stronger statement than "formatted by hand":

```
CLEAN   .agents/skills/gala-rewrite/SKILL.md
```

All seven table rows begin and end with `|` on one physical line.

One inconsistency was introduced and caught this way: the three preflight bullets sat under a lead-in saying "Two facts". The count was removed rather than kept in sync, because a count is exactly the kind of thing that rots.
