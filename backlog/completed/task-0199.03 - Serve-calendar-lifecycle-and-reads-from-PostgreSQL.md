## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Route all calendar integration reads and writes to the PostgreSQL repository added in TASK-0199.02 and stop serving calendar fields from the retained MongoDB `users` document.

Update sign-in (`server/routes/auth.go`), the add/remove/toggle/toggle-sub-calendar and calendar-options handlers (`server/routes/user.go`), token refresh (`server/services/auth/auth.go`), calendar fetching (`server/services/calendar/calendar.go`), contact search (`server/services/contacts/contacts.go`), and the middleware/account overlay (`server/middleware/auth.go`, `server/db/users.go`).
Preserve the existing API response shape and key semantics so the frontend is unaffected.
No PostgreSQL failure may fall back to the retained MongoDB document for calendar authority.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Deliverables
1. `server/accounts/calendar.go`: PostgreSQL-authoritative boundary translating between `pgstore.CalendarAccount`/`CalendarPreferences` and `models.CalendarAccount`/`models.CalendarOptions`. Load a session user (profile + calendar), save/upsert a connection with its credentials and sub-calendars, delete a connection, set connection and sub-calendar enabled state, sync a provider sub-calendar set, save calendar preferences, and update a refreshed OAuth access token. No MongoDB fallback.
2. `server/postgres/calendar.go`: add a targeted access-token refresh write so refresh never rewrites or drops other credentials.
3. `server/middleware/auth.go` and `server/routes/auth.go`: build the auth user from the PostgreSQL account plus PostgreSQL calendar state; sign-in/OTP no longer ensure or read the retained integration document.
4. `server/routes/user.go`: add/toggle/remove/toggle-sub/calendar-options/getCalendars persist only through the accounts calendar boundary.
5. `server/services/auth/auth.go`: token refresh persists to PostgreSQL.
6. `server/services/calendar/apple_calendar.go` and `addAppleCalendarAccount`: consume plaintext passwords; the PostgreSQL repository owns AES-GCM encryption at rest.
7. `server/routes/postgres_group.go` and `server/routes/events.go`: resolve calendar-availability respondents from PostgreSQL.

Verification
- `cd server && go build ./... && go vet ./...`
- `docker compose --env-file .env.test -f compose.yaml -f compose.test.yaml run --rm server-route-test go test ./... -count=1`

Tests
- Rewrite the retained-integration route contracts to assert PostgreSQL calendar writes and no MongoDB calendar writes.
- Cover add (ICS), toggle, toggle-sub, remove, options, and token refresh against the PostgreSQL store.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Routed all calendar integration reads and writes through the PostgreSQL repository and removed the retained MongoDB users document from calendar authority.

What changed:
- server/accounts/calendar.go (new): the PostgreSQL-authoritative calendar boundary. Translates pgstore calendar rows and preferences to the internal models.User shape, loads a session user (profile + PostgreSQL calendar) with no MongoDB fallback, and persists connections with credentials and sub-calendars, deletes connections, sets account/sub-calendar enabled state, syncs provider sub-calendar sets, writes preferences, and updates refreshed OAuth access tokens.
- server/postgres/calendar.go: added UpdateCalendarOAuthAccessToken, a targeted encrypted access-token/expiry write that preserves the refresh token, scope, and other credentials.
- server/middleware/auth.go: builds the auth user from the PostgreSQL account and PostgreSQL calendar state; no longer ensures or reads the retained MongoDB integration document.
- server/routes/auth.go: sign-in and OTP sign-in load and persist calendar connections and preferences only through the accounts boundary.
- server/routes/user.go: add/toggle/remove/toggle-sub/calendar-options/getCalendars persist only through the accounts boundary; Apple passwords are passed plaintext and the repository owns AES-GCM at rest.
- server/services/auth/auth.go: RefreshUserTokenIfNecessary persists refreshed access tokens to PostgreSQL and never writes the retained document.
- server/services/calendar/apple_calendar.go: consumes the repository-decrypted password instead of the legacy AES-CFB value.
- server/routes/postgres_group.go and server/routes/events.go: calendar-availability respondents resolve credentials from PostgreSQL.
- server/db/users.go: GetUserById/GetUserByEmail strip retained calendar fields so the account overlay never serves MongoDB calendar state.

Tests:
- Rewrote the retained-integration route contract to assert PostgreSQL calendar writes and no MongoDB calendar writes (add ICS, toggle, options, remove).
- Updated session-adoption and calendar-removal contracts to seed/assert PostgreSQL calendar state and prove the retained document is ignored and untouched.
- Moved the group calendar-availability fixture to PostgreSQL.
- Added a services/auth token-refresh persistence unit test and a db account-overlay unit test.

Evidence: `docker compose --env-file .env.test -f compose.yaml -f compose.test.yaml run --rm server-route-test` passes for all packages (routes, postgres, services/auth, db, accounts, scripts). `go build ./...`, `go vet ./...`, and gofmt are clean for changed files. No Markdown changed. Browser e2e calendar flows are planned in TASK-0199.07.
