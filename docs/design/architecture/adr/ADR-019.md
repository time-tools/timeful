# ADR-019: Resolve Accounts By External User Identifier

> **Inactive.**
> Superseded on 2026-09-12 by [ADR-021](ADR-021.md).
> Retained for decision history and must not be followed as a current decision.

ADR-021 makes `platform_identities.id` the sole account identifier.
The single-account-identity principle survives in ADR-021; the `external_user_id` resolution statements do not.

## Context

Every external account reference must resolve to exactly one account identity.
An external account reference is a reference to an account by its stable 24-character hexadecimal identifier rather than its internal PostgreSQL UUID, and it appears in the sign-in session as `userId` and in cross-record columns such as `postgres_events.owner_external_id`, the `account_user_id` columns, `access_transfers.external_user_id`, and `account_deletion_tombstones.external_user_id`.
The name "external" is historical rather than a source statement: the identifier was a MongoDB-era account identifier external to PostgreSQL, and after the MongoDB retirement the application mints the identifier and PostgreSQL owns it, so no second store and no third-party provider supplies it.
Request paths must resolve accounts without a compatibility lookup.
Public event URLs are allowed to change, so the design does not need a permanent compatibility map for event identifiers.

## Considered Options

- Keep a permanent generic identifier table for every entity and reference.
- Preserve every event identity so that all old links keep resolving.
- Resolve accounts through `platform_identities.external_user_id`.
- Store external identifiers as extra columns on each PostgreSQL table.

## Decision Outcome

Chosen option: "Resolve accounts through `platform_identities.external_user_id`", because it gives every account reference one resolution point, keeps request paths free of a compatibility lookup, and matches the allowed change of public event URLs.
`platform_identities.external_user_id` holds the account's 24-character hexadecimal identifier, is unique, and is created idempotently through `FindOrCreatePlatformIdentity`.
The application mints that identifier for a new account and PostgreSQL stores it, so the identifier is not supplied by a second store or a third-party provider and carries no authority beyond the account it names.
The sign-in session stores that identifier, and the repository resolves the authoritative account through it.
Records that reference an account store that identifier directly in their own columns, and no permanent generic identifier table exists that remaps the identifier or carries a per-entity legacy identifier.
Distinct accounts remain distinct even when their emails compare equal, because equal email addresses do not establish one identity.

This decision supersedes [ADR-012](ADR-012.md), which resolved accounts during the migration.
The single-authoritative-store boundary is decided in [ADR-018](ADR-018.md).

## Consequences

- Good, because account references resolve through one stable identifier without a compatibility table.
- Good, because the schema stays clean and request paths have no second lookup.
- Bad, because a changed event identifier stops resolving at its old public URL.
- Bad, because equal-email accounts are not merged, so duplicate-looking accounts can persist by design.
