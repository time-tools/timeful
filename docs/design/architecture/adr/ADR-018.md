# ADR-018: PostgreSQL Is The Single Authoritative Store

## Context

The system stores accounts and profiles, events of every kind, responses, attendees, signup data, availability groups, folders, folder membership, calendar integrations, OTP challenges, and historical daily user logs.
Under [ADR-011](ADR-011.md), PostgreSQL was authoritative for core records while MongoDB retained calendar connections and provider tokens, calendar preferences, OTP challenges, friend requests, and historical daily user logs, so some request paths read from both PostgreSQL and MongoDB.
Every record kind must have exactly one authoritative store, every account reference must resolve to one account identity, and no mutation may be authored in both PostgreSQL and MongoDB.

## Considered Options

- Keep MongoDB as a permanent second store for integrations and supporting data.
- Dual-write each mutation to PostgreSQL and MongoDB during a transition period.
- Make PostgreSQL the single authoritative store for every record kind.

## Decision Outcome

Chosen option: "Make PostgreSQL the single authoritative store for every record kind", because it removes the cross-store joins between PostgreSQL and MongoDB, gives every record one authority, and avoids a permanent dual-write path.
PostgreSQL serves the reads and writes of every record kind.
MongoDB holds no record kind, no compatibility redirect serves a record from MongoDB, and no record is authored in both PostgreSQL and MongoDB.
MongoDB is fully retired: no runtime, driver, configuration, or collection remains, and the deprecated [ADR-017](ADR-017.md) retains the removal order as decision history.
No record may create, merge, rename, or authorize an account, and account references resolve through `platform_identities.id` as decided in [ADR-021](ADR-021.md).

The data ownership boundary is:

- Calendar connections, encrypted provider credentials, sub-calendars, and calendar preferences are PostgreSQL-owned.
- OTP challenges are PostgreSQL-owned with their expiry and lockout semantics, and grant no account authority.
- Historical daily user logs and their memberships are PostgreSQL-owned.
- Event-creator and active-user reporting read PostgreSQL records that the system already owns, so no reporting data is copied again.
- Friend requests are dormant, so they are retired and no PostgreSQL table replaces them.

This decision supersedes [ADR-011](ADR-011.md), which kept PostgreSQL authoritative for core records while MongoDB retained integrations, and [ADR-016](ADR-016.md), which restated the data ownership boundary.
The provider-credential encryption boundary is decided in [ADR-020](ADR-020.md), and the durable record-kind boundaries are recorded in [PostgreSQL Data Boundaries](../../../../server/docs/postgres-data-boundaries.md).

## Consequences

- Good, because a record has exactly one authority and no request path joins across PostgreSQL and MongoDB.
- Good, because backup, retention, and recovery cover one store instead of two.
- Good, because no permanent dual-write path between PostgreSQL and MongoDB exists to reconcile.
- Good, because dormant friend-request storage is removed instead of carried forward.
- Bad, because every new record kind must fit the PostgreSQL schema instead of a purpose-built document store such as MongoDB.
