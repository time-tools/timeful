# ADR-022: Use OpenObserve As The Self-Hosted Observability Platform

## Context

The system runs one Docker Compose stack per environment on a single deployment host, where staging and production share one Caddy edge and the host has a total memory budget of 4 GB.
The server records plain-text diagnostics through `server/logger` to a file volume and to its standard streams, and GIN writes text access logs, so the file volume is the only diagnostic store and there is no log search, no metrics, and no traces.
[QR-010](../../../requirements/quality/qr/QR-010.md) requires an operator to correlate a failed staging or production request with structured diagnostic records and service health, and [QR-004](../../../requirements/quality/qr/QR-004.md) prohibits credentials, secrets, anonymous edit tokens, and token-bearing URLs and headers in diagnostics.
Local agents and developers debugging the application need to inspect logs and traces on the development machine itself without reaching the deployment host.
Product analytics is already served by PostHog, so this decision concerns operational diagnostics rather than product analytics.
An observability platform for this system must cover logs, metrics, and traces, run inside the existing Docker Compose topology with low operational and memory overhead, remain actively maintained, and be deployable without Kubernetes, a separate query engine such as ClickHouse, or object storage.
The database-per-environment and shared-edge topology is decided in [ADR-018](ADR-018.md), and the deployment environment contract is recorded in [Environment Files](../../../environments.md).

## Considered Options

- Retain file logs only and add no observability platform.
- OpenObserve in single-node open-source mode with local-disk storage.
- SigNoz, which requires ClickHouse and a multi-service stack.
- VictoriaMetrics and VictoriaLogs with Grafana, which assembles separate tools and adds a visualization dependency.
- A managed observability service, which sends operational data to a third party and works against the project's self-hosted, data-control direction.

## Decision Outcome

Chosen option: "OpenObserve in single-node open-source mode with local-disk storage", because it covers logs, metrics, and traces in one actively maintained platform, runs as a single binary inside the existing Compose topology, and fits the deployment host's 4 GB memory budget when its caches and buffers are explicitly capped.

The deployed edition is the open-source edition in single-node mode with SQLite metadata and local-disk storage, so the system adds no Kubernetes, no object storage, and no separate query engine.
The image is pinned by digest to release v0.92.2; adopting the 1.x line requires a separate compatibility review, and every upgrade is a deliberate change rather than a floating tag.
Staging and production send observability data to one instance on the deployment host, each as its own organization with its own streams and environment-scoped ingestion credentials, and each organization's credentials grant access only to that environment's data.
The development stack runs its own OpenObserve instance on loopback in the default Compose stack, so local agents and developers can inspect logs and traces while debugging; development data stays on the development machine and is never sent to the shared instance.
The platform is adopted for logs, metrics, and traces, and the first delivered signal is server logs.
The server emits OpenTelemetry OTLP records directly to OpenObserve with the OpenTelemetry Go SDK, so no sidecar log shipper, log-parsing pipeline, or Docker log-driver plugin is added, and the existing local diagnostic output remains available.
The OpenObserve listener binds to loopback only, operators reach the UI through an SSH tunnel, ingestion uses authenticated credentials over the internal Compose network, and no Caddy route exposes the platform.
Observability data is retained for 14 days and then deleted, for every signal.
The instance runs with explicit limits for the memory cache, the query engine memory pool, the memtable, and the disk cache, because the defaults consume all available memory and would compete with the application on the 4 GB host.
Anonymous telemetry is disabled.
OpenObserve's AGPL-3.0 license matches the repository's AGPL-3.0 license.
PostHog remains the product analytics tool, and OpenObserve is the operational observability platform; neither replaces the other.

This decision enables [QR-010](../../../requirements/quality/qr/QR-010.md) and constrains [QR-004](../../../requirements/quality/qr/QR-004.md) and the observability requirements recorded in [QR-015](../../../requirements/quality/qr/QR-015.md), [QR-016](../../../requirements/quality/qr/QR-016.md), [QR-017](../../../requirements/quality/qr/QR-017.md), [QR-018](../../../requirements/quality/qr/QR-018.md), and [QR-019](../../../requirements/quality/qr/QR-019.md).
No requirement depends normatively on this record, and no earlier decision is superseded.

## Consequences

- Good, because one platform covers logs, metrics, and traces, so the deployment host and its operators carry less operational load than a multi-service stack.
- Good, because OpenObserve ingests OpenTelemetry OTLP and queries with SQL and PromQL, so instrumentation and operator knowledge are not vendor-specific.
- Good, because local agents and developers gain the same signal visibility in the development stack that operators have in staging and production.
- Good, because the open-source edition's AGPL-3.0 license matches the repository license, and the single-node mode scales from local development to terabytes per day without a topology change.
- Bad, because 4 GB is a tight memory budget, so the explicit cache, memtable, and query-pool caps must be maintained through every upgrade to keep the platform from competing with the application.
- Bad, because observability data lives only on local disk and is not backed up; it is expendable by design, but it disappears with its volume.
- Bad, because the open-source edition lacks enterprise features such as SSO, RBAC, and audit trails, so access control relies on network restriction and environment-scoped credentials.
- Bad, because release v0.92.2 predates the 1.x line, and moving to 1.x requires a deliberate compatibility review.
- Bad, because stored records are immutable, so incorrect or sensitive data cannot be selectively corrected and can only age out through retention or be dropped with its stream.
- Bad, because a second diagnostic sink widens the QR-004 surface, so every shipped record must already exclude credentials, secrets, anonymous edit tokens, and token-bearing URLs and headers.
